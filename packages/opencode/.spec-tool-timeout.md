# Spec: Configurable Tool Timeout + Task Tool Grace Period

## Problem

The global `TOOL_TIMEOUT` (15 minutes) in `tool.ts:8` is hardcoded. It wraps every tool call including the Task tool. When an LLM sets a longer timeout on a Task call (e.g., `timeout: 1800` for complex research), or when `config.experimental.task_timeout` is set higher, the outer `Tool.define` wrapper kills it at 15 minutes regardless. The watchdog `MAX_RUNNING` in `bootstrap.ts:22` is also hardcoded to 15 minutes and must stay in sync.

## Goals

1. Make the global tool timeout configurable via `config.experimental.tool_timeout`
2. For the Task tool specifically: compute its effective timeout and give the global wrapper enough headroom (+ 60s grace) so the Task tool's own timeout fires first and produces a clean error with `task_id` for resumption
3. Keep the watchdog in sync with both configured timeouts
4. Preserve the safety net: genuinely stalled tools are still detected and killed
5. No changes to the Task tool's own timeout logic — it already works correctly

## Non-Goals

- Changing per-tool timeouts (Bash, LSP, WebSearch, etc.)
- Changing the permission auto-approve timeout
- Changing the Task tool's own deadline/resumption logic
- Changing the watchdog's leaf-filtering algorithm

## Design

### Change 1: Config schema — add `tool_timeout`

**File: `packages/opencode/src/config/config.ts` ~line 1183**

Add `tool_timeout` to the `experimental` object, after `task_timeout`:

```ts
tool_timeout: z
  .number()
  .int()
  .positive()
  .optional()
  .describe(
    "Global timeout in milliseconds for individual tool executions (default: 900000 = 15 minutes)",
  ),
```

### Change 2: `Tool.define` — configurable timeout with task-specific grace

**File: `packages/opencode/src/tool/tool.ts`**

Key changes:

- Import `Config`
- Keep `const TOOL_TIMEOUT = 15 * 60 * 1000` as the default
- Read config at execution time (not init time) for each tool call
- **Scoped to `id === "task"` only**: compute the Task tool's effective timeout and add 60s grace. This ensures the Task tool's own `abortAfterAny` at `task.ts:206` fires first, producing its clean error message with `task_id`.
- For all other tools: use the configured global timeout

The `Tool.define` function receives `id` as its first argument, so we can check `id === "task"` in the wrapper.

Current code (lines 60-78):

```ts
toolInfo.execute = async (args, ctx) => {
  // ...validation...
  const deadline = abortAfterAny(TOOL_TIMEOUT, ctx.abort)
  try {
    const result = await raceSignal(
      execute(args, { ...ctx, abort: deadline.signal }),
      deadline.signal,
      "Tool execution exceeded 15min global timeout",
    )
```

New code:

```ts
toolInfo.execute = async (args, ctx) => {
  // ...validation...
  const cfg = await Config.get()
  const base = cfg.experimental?.tool_timeout ?? TOOL_TIMEOUT
  let ms = base
  if (id === "task") {
    const GRACE = 60_000
    const effective =
      typeof args?.timeout === "number"
        ? args.timeout * 1000
        : (cfg.experimental?.task_timeout ?? 600_000)
    ms = Math.max(base, effective + GRACE)
  }
  const deadline = abortAfterAny(ms, ctx.abort)
  try {
    const result = await raceSignal(
      execute(args, { ...ctx, abort: deadline.signal }),
      deadline.signal,
      `Tool execution exceeded ${Math.round(ms / 1000)}s global timeout`,
    )
```

**Why this handles C1**: If the user sets `tool_timeout: 300000` (5min) but doesn't set `task_timeout`, the Task tool's effective timeout is its default 600_000 (10min). The wrapper computes `Math.max(300_000, 600_000 + 60_000) = 660_000`, giving the Task tool 60s of headroom to fire its own timeout and return cleanly.

**Why this handles C2**: The `args.timeout` inspection is scoped inside `if (id === "task")`. No other tool is affected. If a future tool adds a `timeout` parameter, it won't accidentally trigger this logic.

**Why this handles m2**: Error message uses seconds (`Math.round(ms / 1000)s`) instead of rounded minutes, giving precise information.

### Change 3: Watchdog — respect both configured timeouts

**File: `packages/opencode/src/project/bootstrap.ts`**

The watchdog must use a cutoff that respects both `tool_timeout` and the Task tool's effective maximum. Otherwise a task tool running for 20 minutes (within its configured timeout) would be killed by the watchdog.

The Task tool's effective timeout can vary per-call (LLM sets `args.timeout`), but the watchdog can't know per-call values. It should use the config-level maximum as its floor.

Current code (lines 167-171):

```ts
function watchdog() {
  const timer = setInterval(() => {
    watchdogTick(Date.now() - MAX_RUNNING)
  }, WATCHDOG_INTERVAL)
  timer.unref()
}
```

New code:

```ts
function watchdog() {
  const timer = setInterval(async () => {
    const cfg = await Config.get()
    const base = cfg.experimental?.tool_timeout ?? MAX_RUNNING
    const task = cfg.experimental?.task_timeout ?? 600_000
    const grace = 60_000
    const max = Math.max(base, task + grace)
    watchdogTick(Date.now() - max)
  }, WATCHDOG_INTERVAL)
  timer.unref()
}
```

**Why this handles M1**: The watchdog's cutoff is `Math.max(tool_timeout, task_timeout + 60s)`, matching the global wrapper's logic for the Task tool. A task running within its configured timeout won't be killed by the watchdog. The 60s grace matches the wrapper's grace, so the watchdog fires after the wrapper (which fires after the Task tool's own timeout).

**Note**: `Config.get()` is async but cached after first load. The `setInterval` callback being async is fine — unhandled rejections are the only concern, but `Config.get()` is reliable. `watchdogTick` itself remains synchronous.

**Note on per-call `args.timeout`**: The watchdog cannot know per-call timeout values set by the LLM. If the LLM sets `timeout: 1800` (30min) on a Task call, the watchdog uses the config-level maximum which might be lower. This is acceptable: the global wrapper in `tool.ts` handles per-call values correctly, and the watchdog is a last-resort safety net. Users who regularly use long task timeouts should set `tool_timeout` or `task_timeout` in config accordingly.

### No changes to `watchdogTick`

`watchdogTick(cutoff)` is already parameterized — it takes the cutoff timestamp as an argument. No changes needed. Existing tests continue to pass since they provide their own cutoff values.

- `Config.get()` is async; adding it to `tool.ts` execute wrapper is fine (wrapper is already async)
- `Config.get()` in watchdog interval is fine (cached, reliable)
- The task-specific logic is scoped to `id === "task"` — no coupling to other tools
